# Slice 1 architecture

- Scope: Android Flutter triage of every connected Gmail account, offline archive/bundle archive, native Gmail handoff, and live cross-client state (R28). Requirements remain authoritative; this document does not waive R20–R23 or their correction/importance rules.
- Server: one Go binary, standard `net/http`, `pgx`, Google Gmail/OAuth libraries; PostgreSQL owns durable state and the operation outbox. No Redis, message broker, sync framework, or vector extension.
- Phone: Flutter with Drift/SQLite in a background isolate; separate card metadata and message bodies; indexed open-card query renders before networking. Local actions and durable outbox insertion commit together; archived-history scans never occur on startup (R5/R9–R11).
- Gmail: initial INBOX enumeration captures a history watermark first and durably checkpoints each completed page so a failed request resumes at saved progress; Gmail/OAuth HTTP requests have a finite timeout. Subsequently poll `history.list` every 30 seconds, page completely, reconcile affected threads, and advance the watermark only after durable ingestion. Expired history causes full reconciliation, not data loss (R24).
- One account worker owns Gmail reads and writes for that account. It executes pending label changes before reconciliation; desired state overlays pending effects. Gmail history has no actor identity: match effects/state, never pretend history identifies the originating client.
- A card represents one account/thread; archive targets the explicit message IDs observed by the client, not future messages. Removing INBOX never trashes/deletes. New INBOX messages not covered by the action keep/reopen the card; already-archived targets converge without re-adding INBOX (R7/R24).
- OAuth initially uses an administrative Desktop-client loopback flow, `gmail.modify`, offline access and validated state/PKCE. Credentials stay outside the repository; publish External consent In production, unverified, to avoid Testing's seven-day token rule (R18).
- HTML owner: server MIME parser and sanitizer. Preserve full message HTML/layout and CID images; strip scripts, forms, refreshes, event handlers and unsafe URL schemes. Test charset and multipart handling.
- Strip tracker URLs using a vendored, attributed MailTrackerBlocker snapshot plus pre-fetch tiny/invisible-image heuristics, including CSS/image references and tracker links. Fetch remaining images only after checking URLs and redirect destinations; reject private-network destinations/DNS rebinding. Inline image bytes as data URIs for the smallest self-contained offline representation (R19).
- Renderer: Android WebView, JavaScript disabled, CSP forbidding remote resources/forms/frames, navigation intercepted. Show one complete message at a time with thread-message navigation. Neither sanitization alone nor a web Gmail URL proves native Gmail handoff: both need device gates (R8/R19).
- Clustering is an immediate server pass over open mail cards across all accounts in one tenant. It uses the local Ollama embedding API when configured; if Ollama cannot embed, the pass falls back to the existing sender-key assignment. Nearest-centroid cosine matching forms multi-card topics, while unmatched cards remain standalone (R23).
- Take-out stores a tenant-scoped sender-and-bundle exclusion, so the corrected sender stays separate from that topic on later passes. Importance remains independent of topic assignment.
- Live channel: `GET /v1/events` is tenant-scoped SSE carrying `{cursor}` invalidations, with heartbeat and reconnect. PostgreSQL NOTIFY after commit wakes subscribers; clients pull durable changes, so dropped notifications cannot lose state (R29).
- Deployment: home server listens privately; home-initiated reverse SSH tunnel reaches the VPS HTTPS proxy. Proxy applies 60 requests/minute per client address; streaming buffering is disabled. Only generic templates enter the repository (R15/R17).

## Public contracts
- IDs are UUID strings unless explicitly Gmail IDs; cursors are decimal strings; times are UTC RFC3339; tenant/device identity always comes from authentication, never request JSON.
- `POST /v1/devices/enroll {code,name}` returns `{device_id,token}` after atomic single-use redemption. Store token/code hashes only. Every other data request checks revocation and fails with 401/no data when unauthenticated; administrative CLI creates tenants/invites and revokes devices.
- `POST /v1/ops {ops:[{op_id,kind,card_id,args}]}` returns `{results:[{op_id,status,cursor}]}`; status is applied, duplicate, skipped or rejected. Same ID plus different payload is rejected. Commit receipt, state and Gmail effects atomically; device outbox survives lost replies and process death.
Other mail args: snooze `{until,message_ids}`, pin `{pinned}`, reorder_pins `{card_ids}`, take_out `{bundle_id}`. Server orders accepted operations; snooze wakes on a server timer within one minute with no client, and new incoming mail cancels snooze. Pin maps to STARRED; pin order remains local-product state (R20/R21).
Bundle archive and done are separate actions: each changes only open, unpinned members; pinned cards remain open. The server enforces this independently of client visibility (R3/R22).
- `GET /v1/changes?after=cursor&limit=200` returns `{changes:[{seq,entity,id,value}],next,more}`. Entities are account, bundle, card and message; value null is a tombstone. Each transaction locks the tenant counter before allocating distinct seq values, preventing out-of-order commits from hiding changes.
- `GET /v1/snapshot` returns all current active metadata and a consistent watermark; paginate in an explicit snapshot session if necessary. Replay changes after that watermark; never substitute an ordinary live keyset scan with a guessed final cursor.
- Card values contain account_id, gmail_thread_id, state, bundle_id, pinned_rank, snooze_until, subject, sender, sort_at, message_ids and version. Account values expose display address/status, never OAuth secrets. Message metadata includes RFC Message-ID and immutable body hash.
- `POST /v1/bodies {message_ids:[uuid]}` returns `{messages:[{id,body_hash,html,text}],remaining:[uuid]}` with a bounded byte budget and at least one admissible message. Bodies include embedded images; batch fetching respects proxy limits. A card is fully synced only when all required bodies are durable locally.
- Sync merges server state underneath pending local operations. Retain each optimistic operation until its receipt cursor has been pulled, removing the receipt and overlay atomically; no acknowledgment-to-pull resurrection gap. Offline/reconnect retries are silent and never block UI.

## Storage and ownership
- All domain tables include tenant_id; composite PK/FK constraints prevent cross-tenant references. Non-owner runtime role uses RLS with transaction-local tenant context; narrowly scoped SECURITY DEFINER authentication/enrollment functions handle pre-tenant lookup. Migration metadata is database infrastructure, not user data.
- Tables: tenants(id,next_seq); devices(tenant_id,id,token_hash,revoked_at); invites(tenant_id,id,code_hash,consumed_at); accounts(tenant_id,id,address,refresh_token,history_id,gmail_initial_sync,gmail_initial_page_token,gmail_initial_history_id,status); gmail_initial_sync_threads(tenant_id,account_id,thread_id); cards(tenant_id,id,account_id,gmail_thread_id,state,bundle_id,pinned_rank,snooze_until,version); messages(tenant_id,id,card_id,gmail_message_id,labels,html,text,body_hash).
- Tables continued: bundles(tenant_id,id,title,centroid); exclusions(tenant_id,id,bundle_id,card_id,embedding); ops(tenant_id,op_id,device_id,payload_hash,payload,result,cursor); gmail_effects(tenant_id,id,op_id,account_id,message_id,add_labels,remove_labels,state); changes(tenant_id,seq,entity,id,value). Unique effect identity prevents duplicate logical effects on retry, not unverifiable exactly-once remote HTTP calls.
- Layout: `server/cmd/litterbox/` wires commands; `server/db/` owns SQL/RLS; `server/internal/{auth,syncapi,cards,gmail,mailhtml,bundles}/` own the named behaviors. `app/lib/{store,sync,ui}/` owns local projections, transport and screens. `tools/fixtures/` owns sending/manifest generation; `deploy/` owns generic service/tunnel/backup templates.
- Backups: daily PostgreSQL dump, 14-day retention, unencrypted copy to a second owner-controlled machine, weekly restore into an isolated scratch database; restore proof includes body content and tenant relations (R13).
- Acceptance uses genuinely sent LB1 fixtures across all owner accounts, recording account/message IDs privately. Gmail import may support disposable tests but does not replace the required sent-mail or Gmail-web scenarios. Test rich offline kill/reopen, duplicate retries, untouched/new mail, two clients within 2 seconds, 50,000 local archived cards with first list frame under one second, and cross-tenant denials.

## Qt desktop card actions

- `CardStore` keeps the visible cards, pending operations and body lookups in memory. One storage thread owns its SQLite connection and serializes incremental card/outbox transactions; archive deletes the affected row, not the whole cache. Opening the cache before the window exists and draining commits on shutdown are the only synchronous storage waits.
- Actions optimistically emit row insert/remove/move or `dataChanged` notifications. Ordinary archive, done, snooze and note actions do not sort or reset the list. HTTP transmission remains asynchronous and starts only after the local transaction commits; JSON reply parsing runs outside the GUI thread.
- A failed action restores its changed rows/fields without overwriting unrelated later edits. Failed durable operations retain the existing ordered retry queue and block later transmission until reconnect. Successful acknowledgements delete only their outbox row and do not trigger a full snapshot reload; SSE continues to reconcile server snapshots incrementally.
- Focused regression commands: `tst_cardstore archiveKeepsModelIndexes archiveDoesNotWaitForDatabaseLock archiveFailureRestoresRowWithoutReset rejectionRetainsHeadAndBlocksLaterOps -platform offscreen`, and `tst_api` for HTTP success, bearer-denial and JSON array contracts. The 1500-card archive test reports GUI-call time; 16 ms is a proposed responsiveness target, not a sourced or platform-independent guarantee.
- Mail navigation keeps one lazily created `MailDetailPage` and its browser alive for the window lifetime; each open replaces the selected card properties and reloads its cached body. StackView receives the existing item, so back/close does not destroy the reader.
- Desktop mail startup is shared by the app and its runners in `MailDocumentProfile::initialize()`, before `QGuiApplication`. On Linux it disables only Chromium GPU rasterization; Qt Quick still renders/presents with the hardware GPU. This avoids Qt 6.11.2's black NVIDIA/Wayland mail bodies when its disabled GBM path falls back to Vulkan textures imported into OpenGL. The policy preserves existing Chromium flags, the sandbox, disabled message JavaScript and the offline resource restrictions. Resize acceptance requires a readable compositor screenshot before measuring; neither `loadProgress == 100` nor a hardware `GL_RENDERER` proves the body was painted.
- The inbox stays visible but disabled behind the opaque reader, and its stack exit/return does not slide the ListView viewport outside the window. This preserves the current delegates and scroll position instead of paying to destroy/rebuild Controls on every open/close. The opt-in `mailresize.qml` open/close oracle exercises Google, NYT, LinkedIn and a mid-list card with unchanged card IDs and scroll position; `mailresize_driver.py` records load average and swap usage for paired baseline/candidate runs.
