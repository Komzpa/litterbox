# Shared source ingest

Non-mail collectors use `POST /v1/ingest` with `Authorization: Bearer <source-token>`. A token is bound to exactly one `(tenant, source)`; the request cannot choose either. Upsert JSON fields are `external_id`, `kind`, `title`, `summary`, `at` (nullable), optional `timed`, `note_order`, and `actions`. Use `{"operation":"close","external_id":"..."}` to close that source's card. Upserts retain the same card identity for the same source/external ID. Repeated todo/agent snapshots preserve local dismissal; a newly raised HA notification reopens the card. Other sources are dismissed locally and never invoke callbacks. A Home Assistant (`ha`) source token may have a callback URL; `ingest.OnDone` queues a durable callback transactionally with the canonical card done operation and the server retries failures with exponential backoff. Callbacks are at-least-once; consumers should honor `Idempotency-Key`.

The persisted ingest `kind` is exposed as `source_kind` by `GET /v1/cards`, the initial offline snapshot, and the incremental change feed. `source` remains the token-bound source identity for authorization, card identity, and actions; it is never replaced by the semantic kind. Qt labels `source_kind=reminder` as `reminder`, including after an offline cache restart, while other kinds and older payloads without metadata retain the source label. Native reminders continue to use their existing `source=reminder` label.

## Result files

An upsert with `kind` `research_result`, `proactive_brief`, or `reminder` may carry an optional `files` array: `{"name":"report.pdf","media_type":"application/pdf","data":"<base64>"}`. The limits are 10 files, 8 MiB of decoded data in total, and a 12 MiB request body; requests without files keep the 1 MiB body budget. Files on any other kind, on `close`, or with more files/bytes than allowed are rejected with 400 (413 for size) and store nothing. Reminder files use the same atomic storage, source/tenant authentication, and offline card-body contract as research and brief files.

Each `name` is reduced to its base name and must then be 1-255 bytes without `/`, `\`, NUL or a leading dot. The declared `media_type` is ignored — the server sniffs the bytes — except that a `text/*` declaration stays `text/plain`. The card and its rendered body land in one transaction: the summary is stored as escaped text and each file becomes an RFC 2397 `data:<mime>;name=<pct-encoded>;base64,<b64>` link (plus an `<img>` with the same link for png, jpeg, gif and webp) inside a server-built HTML document in `card_bodies`. An upsert without `files` deletes that card's body row.

`GET /v1/cards/{id}/body` serves that stored document verbatim for non-mail cards (empty `threadId`, `accountId` and `source_url`); mail bodies keep the sanitizer and Gmail URL. `GET /v1/cards` rows carry `has_body` so the client can prefetch the document into its offline cache.

## R27: tasks-loop Telegram after card delivery (read-only finding)

The tasks-loop Hermes overlay `Config/hermes/reemxy/patches/0059-kanban-kanban-watchers-notifier.patch` targets `gateway/kanban_watchers_notifier.py`: `_fmt_completed` constructs the completed-task notification from the event summary (or task result), and `_KanbanNotification.deliver` sends it through the subscriber's platform adapter. The exact cutover is to post that substantive completed research/brief result to this API instead of emitting its completed-result Telegram text: `external_id=task ID + result version`, `kind=research_result` (or `proactive_brief`), a concise `title`, full result as `summary`, and completion time as `at`; use a source-scoped token. Suppress the matching Telegram completion-result notification after a successful ingest, so the same result is not delivered twice. Keep Telegram delivery for urgent alerts and approval requests only; do not convert ordinary assistant replies into cards. Apply the change in the tasks-loop/Hermes source overlay (not this repository); this repository records the required cutover but does not edit tasks-loop.
